# guardrun Threat Model

本書はコードの静的読解に基づく。コメントに記載された過去の実測は、今回確認した実測結果とは区別する。

根拠の `P:行番号` は [guardrun.py](/Users/USER/bin/guardrun.py)、`C:行番号` は [guardrun-crosstest](/Users/USER/bin/guardrun-crosstest) を指す。「非保証の明記」と「実装から分かる限界」を区別し、それ以外は「コードからは決まらない（要確認）」とする。

## 1. 守る対象（資産）

| 資産 | 保護する内容と範囲 | 根拠 |
|---|---|---|
| ファイル | 許可した書き場の外への書き込みを制限する。作業場内の削除・大幅な縮小は差分で検出する。作業場内の変更をすべて禁止する設計ではない。 | P:759–795、832–856、2551–2571 |
| 秘密 | SSH・AWS・GPG・Keychain・設定内の秘密など。囲いでは本人のホームを原則読ませず、必要な場所を戻し、指定した秘密を拒否する。 | P:491–511、608–618、768–794、839–855 |
| ネットワーク | 契約に応じた通信制限。ただし実現する細かさは enforcer に依存する。 | P:638–640、701–713、1358–1364 |
| 機械の資源 | 単一ファイル容量、作業場の増加バイト数・ファイル数、CPU 時間、実行時間、開けるファイル数。終了後に残るプロセスも対象。メモリ・GPU・機械全体の資源上限は、これらと同じ保証には含められない。 | P:513–528、619–624、3793–3823、3983–4007 |
| 記録そのもの | 予告、実行前の状態、受領証、判定。採点される側による読み取り・偽造と、実行中断による記録欠落を防ぐ対象とする。実行可否に使う「証明の控え」も信頼性に関わる。 | P:449–453、1706–1774、2187–2220、3372–3406、3971–3975 |

「記録」は他の壁の破れを認識するための資産であり、コードは「消えないほうが先」と位置付ける。ただし、永久保存を意味しない。完了した記録は既定で最新300件を残し、古いものを削除する。未完の予告は削除対象にしない。（P:449–453、2786、3458–3469）

## 2. 攻撃者モデル

エージェントを敵と決めつけない一方、命令、生成物、出力、完了報告を信用の根拠にしない。以下は悪意・暴走・誤りのいずれでも同じ結果になるため、区別せず対象とする。

- **許可外の場所へ書く。** 作業場の外や誰でも書ける一時領域を使う。（P:1856–1880）
- **秘密を読む。** 指定された秘密だけでなく、ホーム内の未列挙の設定や履歴を読む。（P:501–511、1882–1942）
- **許可外へ通信する。** 外部サイトやローカルサービスに接続する。（P:1944–2033）
- **資源を消費し続ける。** 巨大ファイル、多数の小ファイル、CPU の無限ループ、終了しない処理を作る。（P:2035–2086、2133–2169）
- **子孫を残す。** 別のプロセスグループを作り、親を終了させ、作業ディレクトリも移して探索から外れる。出力パイプを保持して終了処理を待たせる。（P:2171–2185、3299–3316、4013–4025）
- **後で壁の外で実行されるものを置く。** Git hooks・config、npm の install 系 scripts、`node_modules/.bin` など。（P:2088–2131、2464–2487、3605–3643）
- **実際の変更と異なる報告をする。** 別ファイルを変更して「直した」と言う、書いてから消す、失敗を出力や終了コードで誤認させる。（P:2490–2494、2729–2739、2574–2583、4236–4253）（実測で潰し済み 9/24-25: CLI が失敗・赤でも終了コード0を返す、殺せなかった命令を「止めた」と書く → §6 穴-6・穴-12）
- **採点の材料を操作する。** 受領証を偽造する、読めないファイルを置いて差分から隠そうとする、内側の見届け記録を消す・FIFOやリンクに差し替える。（P:2187–2220、2517–2522、2584–2599、2628–2661）（実測で潰し済み 9/24-25: FIFO を残して差分収集を止める、`.git/hooks` をリンクで置く、別 uid の 0700 に書いて差分から隠れる → §6 穴-1・穴-2・穴-4）
- **規則になる入力を細工する。** パス文字列への規則注入はコメントに実例があり、契約生成時の文字検査とエスケープがある。（P:559–564、601–604、733–736）

親の SIGKILL、OOM、電源断などによる「仕事は起きたが受領証がない」状態も対象である。これはエージェントの攻撃に限らない。（P:2222–2228、2744–2766）

エージェントが管理者権限を持つ場合や、OS自体を破る場合まで含む攻撃者能力の上限は、**コードからは決まらない（要確認）**。

## 3. 信用の境界

### 採点される側と受領証の間

実行される命令とその子孫は信用しない側に置く。外側の `run()` が予告を作り、実行前後の状態を採り、受領証を確定する。親が死んだ場合は外側の `sweep()` が未完の予告を拾う。契約は記録の根を必ず「読ませない」に加える。（P:608–612、2763–2777、3372–3406、3475–3517、3860–3884）

**囲いだけでは、壁の外を同じ uid で動くプロセスから受領証を守れない。** この問題はコードに明記されている。壁の中で「記録」の試験が通っても、壁の外から同じ uid で受領証の判定を書き換えられた、という実測コメントがある。（P:859–868）

別 uid と、人側の記録置き場の権限が追加の境界になる。POSIX の別ユーザ執行は「記録・残党」を宣言し、予告生成時には記録の根を700にする。ただし権限設定の `OSError` は握りつぶすため、設定処理があることだけで実機の保護成立とは断定できない。（P:894–900、3380–3390）

### enforcer の宣言と実際の保証

| enforcer | `縛れる壁` の宣言 | 境界・制約 |
|---|---|---|
| `SandboxExec` | 場所・秘密・通信 | macOS Seatbelt。単体では別 uid の境界を作らない。（P:720–727） |
| `Bubblewrap` | 場所・秘密・通信 | Linux のマウント・名前空間。通信は全遮断で、行き先を指定する契約は拒否する。（P:804–855） |
| `別ユーザ` | 記録・残党 | uid 分離。場所・通信は縛れず、秘密も宣言から除外されている。（P:876–900） |
| `重ね` | 内外の宣言の和集合 | 外側を uid 分離、内側を囲いとする。通信粒度は通信を縛る側に合わせる。（P:1214–1242） |
| `素通し` | なし | 囲いがないことを明示する。共通の上限制御と囲いは別物。（P:1298–1313） |
| `Windows別ユーザ` | 記録・残党・秘密・場所・通信 | 別アカウント、NTFS ACL、firewall。場所は列挙式、通信は外向き遮断・loopback 通過。（P:1316–1366） |

`別ユーザ` と `重ね` の説明文には、別 uid が秘密も守るという記述が残る。しかし、後続コメントと実際の `縛れる壁` は、通り道のACLを開けることで秘密が読めたとして秘密を除外している。本書では後者を採用する。（P:878–900、1220–1229）

（実測で潰し済み 9/24-25 → §6: 特権なし Linux で別ユーザ+bwrap が 6○6★ だった件——`setfacl -R` の失敗で2回目が全部拒否、sudo が rlimit を消す——は直して 12○（穴-21）。bwrap が置いてあるのに立たない機械では「見送った囲い」と言ったうえで別ユーザだけの壁で走る（穴-16）。Windows の用意の失敗を拒否にする直し（穴-19）と Job Object による CPU 上限（穴-20）は**実機未検証**であり、潰れたとは断言しない。）

宣言だけで実行を許可するわけではない。要求された壁の試験結果が不成立なら拒否する。ただし `prove=False` や空の `require` では、その判定を通らない。（P:3937–3952）

### 外側に置く必要がある判断と部品

上限、許可パス、通信先、要求する壁、増加の宣言を決める呼び出し側は、信頼側に置く必要がある。特に「増える見込み」は人が決め、モデルの自己申告から導出しないと明記される。（P:3827–3848）

また、信頼側には guardrun 本体、採点・掃除処理、OSの権限・隔離機構が含まれる。それら自体の改変や侵害への対策は、**コードからは決まらない（要確認）**。

### 外側の受領証と、内側の見届け記録は別物

`見届け.txt` は、壁の内側から書ける一時置き場に置かれる。コード自身が、命令と見届け役は同じ権限であり、記録を差し替えられると明記している。（P:2580–2591、4043–4048）

通常ファイルの確認、非追従・非ブロッキングの open、4096バイトの読み取り上限、外側の終了コードとの照合はある。しかし、これを**採点される側から改変不能な証拠**とは呼べない。通常ファイルの内容偽造を含む耐性の全体は、**コードからは決まらない（要確認）**。（P:2628–2661、4190–4198）

## 4. 壁ごとの保証と非保証

ここでいう保証は、該当 enforcer・契約・試験成立を前提とした設計上の約束であり、今回の実機での成立確認ではない。

| 壁 | 約束と確認方法 | 明記された非保証／実装上の限界 |
|---|---|---|
| **場所** | 許可された書き場では書け、外では書けない。試験は作業場内、外、誰でも書ける場所を確認する。（P:1856–1880） | **明記：** 別 uid 単体では `/tmp` 等へ書ける。Windows は列挙式で、塞ぎ漏らした場所には書ける。「既定で全部禁止」ではない。（P:881–884、1338–1342） |

| **量** | `RLIMIT_FSIZE` による**単一ファイル**のサイズ上限。試験は5MBを書こうとして64KiB以内で切れることを見る。（P:2035–2044、3810–3811） | **明記：** 合計容量・inode数を縛らない。「名前が、防げる範囲より広く聞こえていた」。Windowsではこの上限を縛れない。（P:460–465、1343–1346） |

## 5. 保証しない範囲（明示）

**guardrun は、生成物の意味的正しさや無害性を保証しない。** 判定は主に差分・縮小率・削除・特定の仕掛け・終了状態から作る。`check_claim()` も申告パスと変更パスの照合であり、「要求どおり直った」ことの検証ではない。（P:2551–2571、2729–2739、4199–4235）

**guardrun は、許可した作業場の変更を未然にすべて防いだり、自動で元に戻したりする仕組みではない。** 削除・縮小・仕掛けを、変更後に赤判定する処理がある。赤判定は被害が未発生だったことを意味しない。（P:2531–2571、4133–4172）

**受領証は全ファイル・全操作の完全な監査ログではない。** スナップショットは除外ディレクトリ、シンボリックリンク、4,000,000バイト超のファイルを飛ばし、通常の収集件数上限は20,000件である。総量監視とは対象が異なる。したがって「差分に出ない変更は起きていない」というコメントは、監査対象外まで含む事実として採用できない。（P:2461–2462、2490–2533、3664–3669）（実測で潰し済み 9/24-25: 作業場に FIFO などの特殊ファイルがあると収集が永久に止まる穴は、特殊ファイルとして差分に記録する形で潰した → §6 穴-1）

**壁を外した構成に、閉じ込めや改変不能な記録の保証はない。** 「嘘と沈黙だけ」は明示的な劣化モードであり、モデルが家を読み、受領証を書き換えられることまでコメントに記載される。（P:472–489）

**一台・一時点の試験結果を、全OS・将来の状態へ一般化しない。** 実装は証明を既定600秒再利用する。「毎回verifyする」という説明より、実装の有効期限と指紋の条件を優先して読む。指紋に含まれるのは執行名、OS情報、uid、本体の更新時刻・サイズである。（P:1687–1775、3937–3950）

crosstest は、現在の機械、Linux+bwrap、Linuxでbwrapなしの三条件を回す手順である。DockerがなければLinuxは未測定と表示する。Windows、全enforcer組合せ、同一OSの全設定を試すものではない。また、終了コードだけで全壁の合格を表す構成ではなく、出力の各判定を読む必要がある。（C:8–14、23–31、34–64）

OS侵害、管理者による改変、媒体故障、秘密のあらゆる流出経路までを責任外とする正式な線引きは、**コードからは決まらない（要確認）**。明記がないものを、既存の免責として追加しない。

## 6. 実測で見つけて潰した穴（22個・2026-09-24〜25）

## 7. カーネル層で遮断すべきものの候補

以下は、コードに示された限界から導く設計候補であり、導入済みの保証ではない。

| 候補 | 現在のユーザ空間の仕掛けでは足りない理由 |
|---|---|
| **採点側と実行側の権限分離** | 同一 uid の壁外プロセスは受領証を改変でき、記録規約だけでは止められない。コード自身がuidの意味による限界とする。（P:859–868） |
| **総容量・ファイル数の割当時上限** | 一秒周期の走査では、その間に完了する大量生成を事前阻止できない。厳密な上限には割当時に拒否する境界が必要。（P:2047–2053、3983–4007） |
| **走り単位で逃げられないプロセス所属と終了処理** | `setsid`・親の終了で組と親子追跡から外れ、cwd変更でも探索を逃れる。uid一括停止には別の走りを巻き込む問題がある。（P:1192–1194、2171–2179、3299–3316） |
| **Windowsでの許可リスト型ファイル書込制御** | 公共の書き場を列挙してACLで塞ぐ方式は、未列挙の書込可能場所を禁止できない。既定拒否の境界が現在の実装にはない。（P:1338–1342、1459–1464） |
| **Windowsのloopbackを含む通信制御** | 現行firewall方式ではloopbackを止められないと明記される。空の許可先を完全遮断にするには別の境界が要る。具体方式は要確認。（P:1358–1364、1489–1498） |
| **終了証拠の書き手を実行対象から隔離すること** | 見届け役と命令が同じ権限で、見届けファイルを命令から変更できる。通常ファイルの検査と終了コード照合だけでは、書き手の真正性は保証しない。（P:2584–2599、2628–2661、4190–4198） |

仕掛けの意味判定や「依頼どおり修正したか」は、カーネル遮断だけで解決できるとコードからは言えない。そのため上表には含めない。

## 読み取れなかったので確認が要ること

以下はいずれも **コードからは決まらない（要確認）**。

- **実機で現在成立する壁。** 今回は読み取りだけであり、過去の実測コメントも現在の成立証明にはしていない。
- **攻撃者の権限上限。** 管理者権限、OS侵害、壁外での同一uid実行をどこまでモデルに含めるか。（P:859–868）
- **外側の保護。** guardrun本体、wrapper、証明の控え、掃除処理を誰が変更できるか。（P:1706–1749、3836–3841）
- **契約の決定権。** `require`、`prove`、許可パス、上限、増加宣言を、実際の呼び出し側がエージェントから独立して決めているか。（P:3827–3841、3937–3952）

- **秘密の経路。** 環境変数、許可した読取領域、許可先サービス経由の秘密取得をどこまで扱うか。（P:618、790–794、3957–3959）
- **記録試験の不成立判定。** 読取結果が数値でない場合に「記録」の試験が通りうる実装をどう扱うか。（P:2203–2220）
- **内側の終了記録の真正性。** 通常ファイルの内容操作と、外側終了コードが整合する操作への耐性。（P:2628–2661、4190–4198）
- **掃除の稼働保証。** 誰がいつ起動し、停止をどう検知し、期限超過通知を誰が受け取るか。（P:3475–3517）
