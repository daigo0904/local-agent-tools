# ⑤ 比較評価の設計（2026-09-24）

**走らせる前に、何を測るかと判定基準を決めておく。** あとから都合よく解釈しないため。

## 比べる3つ

| 腕 | 中身 |
|---|---|
| A. 防御なし | そのまま実行。壁も受領証も無い |
| B. 現行 guardrun | uid 分離 + sandbox-exec（macOS）／bwrap（Linux） |
| C. OS境界を足す | ③のカーネル層 PoC を重ねる |

## 測る3つ（ぜんぶ出す。1つでも欠けたら比較にならない）

1. **防げた数** … 事故の事例（④の Failure Corpus）のうち、止められた件数
2. **正当な作業を止めた数** … 正しい作業の事例のうち、誤って止めた件数
3. **処理時間** … 同じ作業を通したときの壁時計

**2 を出さない比較は無意味である。** 全部拒否すれば 1 は満点になる。
評価層（~/評価層）で今夜まさにこれを踏んだ——嘘だけ測っていると、
「何にでも鳴る見張り」が満点を取る。対照群を同数用意して初めて誤検知が数になる。

**3 を出すのは、止められても遅すぎれば使われないから。**
guardrun は証明の使い回しで 33.8秒 → 0.3秒 にした経緯がある（2026-09-14）。
壁を足すたびにここが伸びるなら、伸び幅を数で出す。

## 正当な作業の事例（対照群）をどこから取るか

**事故の事例と同じ場所から取らないこと。** ④は受領証の「中断・拒否」から起こすので、
対照は「青・緑」の 84件（青67・緑17）から取る。
**同じ実行系・同じ作業場の形で、結果だけが違うもの**を選ぶ。

## 判定基準（先に決める）

- **C が B より「正当な作業を止めた数」を増やしたら、C は不採用。**
  防げた数がいくら増えても。壁は、止めてはいけないものを止めた瞬間に使われなくなる
- **C の処理時間が B の 2倍を超えたら、その旨を必ず併記する。**
  速さは正しさを買わないが、遅さは採用を殺す
- **A で防げてしまう事例は、事例として弱い。** そういう事例は Corpus から外して数える
  （防御なしでも起きないものを「防げた」に数えると、効果が水増しされる）

  C の中身が決まっていないので、いまは A と B だけ先に測れる
