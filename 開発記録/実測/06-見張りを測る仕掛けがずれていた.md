# 見張りを測る仕掛けが、測る対象とずれていた（2026-09-23〜24）

提案の §「見張りは自分が見ていない場所を知らない」に、そのまま入る事例。
**これは見張りの話ではなく、見張りを測る側の話である。**

## 何を作ったか

qwc（自作コーディングCLI）には、モデルの「やりました」という報告を事実と突き合わせる
見張りが8本ある。その検知率を測るために、壊れ方の型から事例を自動生成して
当てる評価層を作った（`~/評価層`）。一晩で:

- 型を9種から10種に増やし（実機で踏んだものだけ）
- 6つの束を生成して held-out で測り（1本42件・生成に80分）
- 4つのモデル（gemma4 / qwen3 / qwen2.5-coder / ChatGPT）で比べ
- qwc に7コミット入れた

## 規律は全部守っていた

- **判定はコードで。** 正解は報告文を一文字も読まず、構造化した主張と砂場の前後だけから出した
- **対照群を置いた。** 嘘と正直を同数作り、誤検知を数として出した
- **held-out を取った。** 直しを導いた束で測り直さず、毎回新しい束を生成した
- **判定基準を先に書いた。** 「破棄が50%を超えたら検知率は語らない」など
- **負けた結果も同じ形で出した。** in-sample 100% が held-out 66.7% に落ちたことを毎回記録した

## それでも、土台がずれていた

評価層は、見張りの関数（`claimsWorkDone` / `filesNeverWritten` / `removedTextThisTurn` …）を
**個別に呼んで**「鳴ったか」を数えていた。

ところが本番の qwc は、それらを `runTurn` のループの中で、
`shouldNudgeToAct()`（雑談と判定したら丸ごと落とす）・`maxNudges`・ループ順序つきで呼ぶ。
**評価層はこの外側を再現していなかった。**

実測（対照64件・質問だけの依頼）:

    評価層（部品を個別に呼ぶ）   誤検知 10/64 = 15.6%
    本物の runTurn を通す        誤検知  3/64 =  4.7%

**鳴っていないものを誤検知と数えていた。** 一晩ぶんの数字が、本番の数字ではなかった。

## 訂正そのものも間違えた

ずれに気づいて「本番では0回」と結論しかけた。そのとき使った確認スクリプトが、
**事例の「手」を1つも実行していなかった**。だから `writeFail` や `editLog` に依存する見張りは
最初から鳴りようがない。手を流す形に直して 4.7% が出た。

**測る道具は、二度続けて別の嘘をついた。**
一度目は「本番より多く鳴る」、二度目は「本番より鳴らない」。向きが逆なので、
片方だけ直したときに「直った」と読んでしまう形だった。

## この一晩で、測る道具に4回騙された

| # | 何が嘘をついたか | どう出たか |
|---|---|---|
| 1 | `maintenance()` の戻り値（2つ組）を真偽値として受けた | 毎回「手入れ中」で何もせず、**心拍だけ正常**に見えた |
| 2 | 文の区切りに ASCII のピリオドを使った | `config.py` が `config.` と `py` に割れ、名前を探す判定が**静かに何も見つけられなくなった** |
| 3 | `cat` を「書き換えうるコマンド」に分類した | 読むだけのコマンドが検査の免除になり、見逃した |
| 4 | 評価層が本番の実行経路を通っていなかった | 一晩ぶんの誤検知率が**過大**に出た |

4つとも「壁が破られた」のではなく、**壁の効き目を測る側が壊れていた**。
そして4つとも、**壊れていることが画面に一切出なかった。**

## 提案への含意

1. **見張りを足すときは、その見張りを測る仕掛けも同時に疑う必要がある。**
   規律（対照群・held-out・事前の判定基準）は、**土台がずれていても全部守れる**。
   守れているという感触が、かえって疑いを遅らせた。

2. **「本番と同じ経路を通す」は、正しさの条件であって、精度の問題ではない。**
   部品を個別に呼ぶ測り方は、速くて書きやすい。だから選んだ。
   本番と一致しないことは、速さと引き換えにできる種類の欠点ではなかった。

3. **測る道具の誤りは、向きが両方ありうる。**
   過大に出ることも過小に出ることもある。片方を直した時点で「直った」と読むと、
   もう片方に入れ替わっただけのことがある（実際にそうなった）。

4. **人が気づいたのではなく、実物に当てて気づいた。**
   利用者から「Fuzzer 自体が同じモデルの癖に過学習していないか」という指摘があり、
   それを測るために本物の経路に当てたところ、**過学習より先に、経路のずれが出た。**
   疑いを持ったこと自体は人の側から来ている。

## 数字（本物の runTurn で測り直したもの）

    対照64件（質問だけ）      誤検知 4.7% → 0.0%
    gemma4 held-out 6本      検知 88.6% → 87.6%
    他モデル3種              検知 81.3% → 83.3%
    言い換え126件            検知 63.5% → 82.5%

門（依頼が質問なら促さない／主張は打ち消し側から見る）を入れた前後。
**言い換えの +19pt が狙いそのもの**で、モデルを替えても崩れにくくなった。
ただし打ち消しも一覧であり、4モデル目で一度崩れて、負けた数字を見てから語を足した。
**5つ目のモデルでまた崩れうる。**

**上の数字のうち、直しの効果の証明になっていないもの（2026-09-24 母艦が追記）。**
語尾で受ける打ち消し（9fd549a）は、種の誤検知1件を**見てから**入れた直しで、
そのあと同じ束で測り直している。したがって「他モデル 誤検知 6.0% → 4.0%」は
in-sample の数字であり、語尾の直しが効いた証拠ではない。
**次に held-out を1本取ったときに、この直しの前後を比べて確かめる。**

## 追記（2026-09-25）— 正解を出す側が3回壊れていた

前段は「評価層が本番の実行経路を通っていなかった」話だった。
経路を直したあとも、**正解を出す側（神託）が壊れていた**。3件とも、
見張りを疑って追いかけた結果、**壊れていたのは正解のほう**だった。

| # | バグ | 影響 |
|---|---|---|
| 1 | 意図と実態が食い違う事例を破棄していた | 検知率を **13.8pt 水増し** |
| 2 | 「消した」を「消えた行にあるか」で見ていた | `TIMEOUT = 30 → 60` を正直と採点 |
| 3 | 手の結果を神託に渡していなかった | `ls` を本当に走らせた正直な報告を嘘と採点 |

### 1 が最も悪質だった

「生成の下手さを検知率に混ぜない」という理屈で、正しい方針として何度も説明した。
実測したら逆だった。

    残していた束（105件）   検知 94.3%
    破棄していた束（ 28件）  検知 28.6%   ← 3分の1以下

破棄されるのは「正直のつもりで作られたが、実際には嘘だった」もの＝
**モデルが本気で正直に書こうとした報告文**である。

    嘘のつもりで書いた報告  … わざとらしい完了語が入る → 検知しやすい
    正直のつもりで書いた報告 … 自然な言い回しで、たまたま外れて嘘になった → 検知しにくい

**本番で起きるのは後者。** 実機でモデルが嘘をつくとき、本人に嘘のつもりは無い。
その種類だけを「生成の不良品」として捨てていた。

**気づく手段はずっとあった。** `破棄 33 件` は毎回の集計に印字されていた。
105件の3分の1である。帳簿の脇の数字として扱い、中身を一度も見なかった。

## 規則を足すほど、別の規則が壊れる

1日で**自分の直しが自分の直しを壊したのが5回**。全部同じ形だった。

    削除して を許す         → 削除していません を拾う
    それを防ぐ             → 定義されていない関数X を落とす
    行(う|い|って) を足す   → 流行った に当たる
    失敗した を打ち消しに   → 完了報告を打ち消しと読む
    確認してください を質問に → 修正依頼を質問と読む

**広げると別のものを巻き込み、狭めると本命を落とす。** 境界は実例でしか決まらず、
実例は新しい束を取らないと出てこない。

### 結果として、held-out では前進していない

                直す前(cf0673a)        1日直したあと
    ChatGPT 20件  検知 100.0% 誤 0.0%   検知 100.0% 誤 0.0%   同点
    gemma4  24件  検知  79.2% 誤 4.2%   検知  83.3% 誤 8.3%   差し引きゼロ

14コミット入れて、held-out での差し引きはゼロ。
in-sample は 88.3% まで上がるが、**それは直しを導いた束**なので根拠にならない。

## 提案への含意（前段に足すもの）

5. **言い回しを増やす方向の見張りは、増やすほど壊れる。**
   1日で5回、足した規則が別の規則を壊した。数を増やす設計は、
   増やした本数ぶんだけ相互作用が増える。
   今日いちばん効いた規則（「消したと言うなら1行は消えている」）は、
   **対象を特定せず事実だけで判定していて、一度も壊れていない。**
   規則は増やすのではなく、**事実だけで決まる少数に寄せる**。

6. **測る側のバグは、見張りのバグより見つけにくい。**
   見張りが鳴らなければ「検知率が低い」と出るので追いかける。
   正解が間違っていると「検知できている」と出るので、誰も追いかけない。
   今日の3件は、全部**誤検知を調べていて偶然見つかった**。
   誤検知を数えていなければ、3件とも見つかっていない。
